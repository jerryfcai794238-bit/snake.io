# 全域 Agent 開發與對話規範

## 1. 對話風格與溝通
- 使用繁體中文，風格輕鬆、精簡、直接。
- 將使用者視為專業協作者，避免基礎說教與高階空泛的建議。
- 有限制時提供最接近的可行方案並簡短說明原因。

## 2. 任務分級與工作節奏
- **Level 0／回答**：不讀檔、不修改；直接回答，不需 Plan。
- **Level 1／唯讀調查**：可讀檔、搜尋、檢查、分析與整理；直接執行，不需 Plan 或核准。
- **Level 2／常規修改**：修改不超過 3 個檔案，且不涉及核心規格、公共 API 或破壞性變更。
- **Level 3／高影響修改**：修改超過 3 個檔案，或涉及核心規格、公共 API、破壞性變更（如刪除、搬移、架構異動、推版）。

## 3. Plan 與核准機制（依工具分流）

### ① Antigravity (自主 Agent)
*   **Plan 載體**：強制使用專屬 Artifact 檔案（如 `implementation_plan.md`）。禁止在對話框內貼出完整 Plan。
*   **核准門檻**：Level 2/3 修改前，必須先生成/更新 Artifact 並引導使用者檢視。只有當使用者在對話框中回覆 **「開始」** 時才視為核准，其餘肯定詞均無效。
*   **出錯修復機制**：在同一任務的「開始」授權下，若執行出錯，可直接修復至原 Plan 目標，不需重新申請授權，除非需要變更原定架構。

### ② Codex (VSCode IDE 插件版)
*   **Plan 載體**：使用 IDE 內建的 Plan UI 或 inline 說明。禁止建立 `implementation_plan.md` 檔案。
*   **核准門檻**：常規修改（L2）透過 IDE 內建的 Accept/Confirm 按鈕或快捷鍵直接核准；高影響修改（L3）需先展示 Plan 步驟，經使用者於 chat 視窗或 UI 確認後執行。

### ③ Codex (桌面版獨立 App)
*   **Plan 載體**：由於無 IDE 內建 Plan UI，Plan 請直接於 Chat 對話框中使用 Markdown 區塊呈現。禁止建立 `implementation_plan.md` 檔案。
*   **核准門檻**：Level 2/3 修改前，在對話框內提出簡短 Plan，並取得使用者文字確認（如「OK」、「開始」、「可以」）後即可執行。

## 4. 開發與編輯安全
- **精確編輯**：採小範圍修改，避免大區塊覆寫造成細節遺失。
- **本機備份**：修改規格、GDD、美術需求、字串表、參數表或版本紀錄前，必須備份至 `scratch/backups/YYYYMMDD_HHMMSS/<original-path>`。
- **備份清理**：只保留最近一次版本更新日往前 3 天內的備份檔，未明確要求時不主動刪除。
- **透明 Diff**：完成後提供變更摘要或局部 Diff，讓修改範圍可核對。
- **工作區優先**：磁碟中的目前內容是真源，不得擅自使用 git checkout、git reset 或清理命令覆蓋未提交變更。
- **格式遵從**：遵守專案既有格式化設定（如 Prettier）。

## 5. 文件與規格同步
- 核心邏輯變更應先確認 GDD 或規格是否需要同步。
- 修改規格、GDD、美術需求、字串表、參數表、版本紀錄時，需同步檢查：UI 文案、圖片引用、Icon/Map/FX/SFX 綁定、參數與版本號。
- 版本紀錄僅在使用者明確要求推版或版更時才更新。

## 6. 自動化驗證與回報
- 修改完成後，必須優先執行專案既有的編譯、測試或 Lint 指令（例如 `npm run test` 或 `tsc`）進行驗證。
- 若無自動化指令，則人工二次核對關鍵字、Markdown 表格、圖片路徑、HTML 標籤平衡與版本號。
- 完成後回報：修改檔案、修改章節、完成重點、驗證結果、備份位置與未驗證事項。
