# 規格管理規範 (Specification Management Rules)

為了確保開發脈絡的可追溯性並簡化流程，Antigravity 必須遵守以下規範：

## 1. 討論階段 (Discussion Phase)
- 在產出正式 GDD 之前，必須先產出實體 `implementation_plan.md` 供使用者查閱。
- 方案必須包含：目標、技術路徑、核心參數、受影響檔案清單。
- **必須獲得核准**後方可執行。

## 2. 執行與透明化階段 (Execution Phase)
- 進入實作時，必須同步產出並更新 `task.md`。
- 透過 `task.md` 實時呈現當前進度（待辦 `[ ]`、進行中 `[/]`、已完成 `[x]`）。
- 完成後，需產出新版號的 `GDD_vX.X.X.md` (存放在根目錄)。

## 2. 變更日誌要求 (Changelog)
- 每份新版 GDD 的頂部必須包含 `## 變更日誌 (Changelog)` 區塊。
- 必須條列標註：**調整項目**、**調整理由**、以及**對應的舊版本號**。

## 3. GDD 完整性原則 (GDD Integrity Principle)
- **禁止閹割**：每一份新版號的 GDD 檔案必須包含**全量**的遊戲機制、數值參數與規則說明。絕對禁止僅產出摘要或簡化版。
- **全量覆蓋**：GDD 必須是唯一的 Source of Truth，確保任何版號的 GDD 都是獨立且完整的規格書。
- **結構繼承**：必須沿用高品質的排版結構（如表格、細部參數清單），確保文檔品質不因版號更新而退化。

## 4. 歸檔與比對
- 舊版 GDD 應保留在 `docs/Old/` 中。
- 產出新版後，應引導使用者利用 VS Code 的「差異比對 (Diff)」功能來檢查變更細節。
